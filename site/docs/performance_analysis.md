# Performance analysis — ZipVoice-Distill INT8, browser WASM vs native

Measured 2026-10-21 on Apple M5 Pro (macOS), Chrome 156 (system install), sherpa-onnx 1.13.8 native (ONNX Runtime CPU).
Raw rows: `benchmarks/results.csv` (153 rows). Table below regenerated by `python3 benchmarks/summarize.py`.
Model files: the exact `.onnx` files from the browser bundle (`scripts/extract-bundle.py`; SHA-256 `encoder.int8` f2de9a76…, `decoder.int8` 3cc2e08a…, `vocos_24khz` bcb3b970…). Bundle = `sherpa-onnx-zipvoice-distill-int8-zh-en-emilia` + fp32 `vocos_24khz.onnx` (per the bundle's README).

## Headline
1. **Browser WASM, 4 steps: warm RTF ≈ 2.0–2.3** (≈ 10–13 s to produce ≈ 5–6 s of audio). Not real-time.
2. **~95% of the time is the flow-matching decoder.** Fixed cost (frontend + encoder + vocoder + reference features) is only ≈ 0.4 s in WASM.
3. **The same models run ~8–9× faster in native sherpa-onnx at the same 1 thread** (RTF ≈ 0.24 vs ≈ 2.1). So the main bottleneck is the **WASM runtime's execution speed, not thread count**.
4. Native thread scaling is modest: 1 → 4 threads gives only ≈ 1.6× (RTF 0.24 → 0.15); 8 threads is no better than 4.
5. Cold ≈ warm in WASM (12.4 s vs 12.1–12.4 s): no meaningful warm-up effect after the model is loaded.

**Browser stage split is therefore inferred, not measured**, from a `numSteps` sweep (decoder runs `numSteps` times; everything else runs once): linear fit `gen_s = fixed + per_step × steps`.

| Runtime (1 thread) | fixed (frontend+encoder+vocoder+ref feat.) | per decoder step |
|---|---|---|
| WASM (Chrome) | ≈ 0.40 s | ≈ 2.80 s |
| native | ≈ 0.06 s | ≈ 0.32 s |

Native direct-ORT stage timings (1 thread, synthetic inputs, T = 937 mel frames ≈ 4 s prompt + 6 s target): decoder **284 ms/step** (×4 = 1.14 s), vocoder **52 ms**, encoder **2 ms**. Together with ≈ 0.2 s of frontend/mel/resample this accounts for the native 4-step total of ≈ 1.4 s. With 4 threads: decoder 159 ms, vocoder 23 ms.
Caveat: random inputs → compute cost only; the real decoder cost depends on T (prompt + target length).

## Runtime vs thread-count (what each comparison isolates)
| Comparison | Isolates | Result |
|---|---|---|
| WASM 1T vs native 1T | **runtime/kernel efficiency** (same models, same threads, same inputs) | ~8.6× (RTF 2.08 → 0.24 on zh) |
| native 1T vs 2T/4T/8T | **thread count** | 1.3× / 1.6× / 1.5–1.6× |
| browser build clamps `num_threads` to 1 | — | thread count can't be varied in the browser |

Inference (not measured): even if WASM threads were available and scaled like native (~1.6× at 4T), RTF would stay around 1.3 at 4 steps. The runtime gap, not threading, is the thing to attack. Possible causes of that gap (**untested hypotheses**): native ORT uses ARM int8 dot-product/i8mm kernels for the INT8 MatMul, WASM SIMD128 does not; memory/allocation overhead in WASM. Do not act on these without profiling.

## Step count as a quality/speed knob (`?steps=N` URL parameter, default 4 = upstream)
WASM warm RTF: steps 1 → 0.56–0.71, 2 → 1.05–1.19, 4 → 2.0–2.3, 8 → 4.0–4.3.
Whisper-small transcription of the output (one sample per cell, synthetic reference voice, headed Chrome):
| steps | zh | en | code-switch |
|---|---|---|---|
| 4 | exact | exact | "…Mitting之后…" (meeting mis-heard) |
| 2 | exact | exact | "…明天之后…" (meeting wrong) |
| 1 | exact | – | broken ("我今天要去吃饭…") |
This is intelligibility only (single sample, tiny ASR) — **naturalness and speaker similarity at fewer steps are unevaluated.** The model is distilled for a small step count but I have not checked which count it was trained for.

## Reference transcript handling
Giving a *wrong* reference transcript (English sentence for a Chinese clip) yields wrong/short output (3.0 s instead of ≈ 5.8 s, ASR garbage). Duration and alignment depend on the transcript, so the UI requirement "exact transcript" is real, not cosmetic.

## Memory
- Chrome process tree RSS (Playwright-launched, headed, `benchmarks/memory.mjs`): idle browser ≈ 0.9 GB → after model load ≈ 1.8 GB → after 3 generations ≈ 2.1 GB, **peak ≈ 2.1 GB** (RSS over-counts shared pages; upper-bound estimate).
- Worker WASM heap 512 MB; page JS memory (`measureUserAgentSpecificMemory`) ≈ 205 MB.

## Streaming
Not streaming. Generation returns after all sentences are done; the per-sentence callback exists but with short texts there is one chunk. Time-to-first-audio = full generation time (≈ 10–13 s at 4 steps).

## Limits of this analysis
- Single machine, single Chrome version; no thermal-throttling study. Page "load" times are from localhost, not a 195 MB network download.
- Synthetic (`say`) reference voices only. No real-speaker similarity result yet.
- Browser per-stage split is a regression estimate; the vocoder vs encoder share in-browser is unmeasured.
- Chrome extension/other browsers (Safari, Firefox) not tested.
